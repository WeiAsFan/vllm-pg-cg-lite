# 2026-08-28 历史预实验结果审计

## 1. 结论

这批结果是有价值的历史预实验，但不是当前 PG-CG Lite 的正式结果。它支持一个后续假设：减少 capture-size 数量可能显著降低 CUDA Graph 捕获时间与显存，而固定工作负载下的吞吐和 median TPOT 可能基本保持不变。它不能证明当前“默认集合子集”规划器有效，也不能证明画像选择优于简单的同预算剪枝。

正式实验必须使用 `fix/pg-cg-lite-hardening` 分支和
[A6000 完整操作手册](a6000-runbook-zh.md) 重新运行 A/B/C；旧归档中的配置、计划和汇总不得直接复用。

## 4. 为什么不能进入正式结果表

### 4.1 候选配置违反当前算法契约

旧 Lite 配置为：

```text
[2, 8, 9, 12, 15, 16, 23, 256]
```

其中 `9`、`12`、`15`、`23` 不属于该次运行的默认 capture-size 集合。当前规划器要求候选集合完全取自默认集合、保留默认最大覆盖上界并满足尺寸预算，因此旧配置不能代表 hardening 分支上的算法。

### 4.2 缺少同预算对照，因果归因不成立

旧实验只有“默认全集”和“旧 Lite”两组。即使捕获开销下降，也无法区分收益来自：

1. 单纯把尺寸数量从 35 减到 8；
2. 画像指导的具体八个尺寸选择。

当前协议增加不读取画像的同预算等秩子集 B 组。A 对 C 描述整体剪枝权衡，B 对 C 才检验画像是否提供额外价值。

### 4.3 旧正确性检查产生了假阳性

旧脚本只检查生成文本数量，没有逐请求比较内容。重新审计详细 JSON 后，跨配置同索引完全一致的请求数分别为：

| 对比 | 完全一致 |
|---|---:|
| 旧默认 A1 / 旧 Lite B1 | 440 / 500 |
| 旧默认 A2 / 旧 Lite B2 | 427 / 500 |
| 旧默认 A3 / 旧 Lite B3 | 438 / 500 |

但同一默认配置不同轮次也不完全一致：A1/A2 为 452/500，A1/A3 为 449/500。这表明真实并发性能模式本身存在批处理相关差异，既不能把跨轮文本不一致直接归因于剪枝，也不能用“数量相同”证明功能等价。

当前协议将两类问题分开：在 `VLLM_BATCH_INVARIANT=1` 的确定性模式下逐字比较 A/B/C，验证功能等价；在显式关闭该变量的真实性能模式下检查全部请求完成、无错误和 token 数符合协议，但不比较跨轮生成文本。

### 4.4 画像和计划证据不完整

归档中的服务记录显示 `cudagraph_metrics=False`，没有可复核的
`PG_CG_PROFILE=` 画像行；汇总中的 profile 字段为空，也没有归档生成候选配置所用的原始画像、`plan.json` 和源配置。这使候选尺寸无法从证据链中重算。

正式实验必须保留默认画像服务日志、机器可读画像行、K=4/8/16 计划、A/B/C 实际配置、计划门禁输出及它们的哈希。

### 4.5 time-to-ready 存在明显缓存混杂

第一轮旧默认与旧 Lite 的 ready 时间约为 156 秒和 56 秒，后续运行约为 37～39 秒。第一轮承担的首次依赖/JIT/缓存成本不相同，因此不能把该差值全部归因于 capture-size 剪枝。

当前协议先在真实非 batch-invariant 模式下分别预热 A/B/C，再按交叉顺序运行九次；报告的是共享缓存已预热后的 time-to-ready，不声称是首次部署冷启动。

### 4.6 归档混入大量缓存

旧归档解压后约 68.2 MiB，其中 vLLM 与 FlashInfer 缓存约 56.17 MiB、744 个文件。这些文件不帮助复核结论，反而扩大归档并模糊证据边界。

正式归档只包含日志、JSON、配置、环境清单、验证输出、汇总、图和 SHA256 清单，明确排除模型、`.venv`、`.cache`、vLLM/FlashInfer 编译缓存及 `.so`、`.cubin`、`.ptx` 等二进制产物。

## 5. 对下一步的约束

旧结果之后的唯一有效推进路径是：

1. 在远端 Linux A6000 上 checkout hardening 分支并固定提交；
2. 通过补丁哈希、CUDA、TorchInductor/Triton、目标 pytest 和 Ruff 门禁；
3. 从真实默认服务日志生成满足默认集合子集契约的 K=8 计划；
4. 在 batch-invariant 模式下完成 A/B/C 功能等价性；
5. 在真实性能模式下完成公平预热、九次 A/B/C 和一次轻量 shift；
6. 自动生成摘要并制作排除缓存、带双层 SHA256 的证据归档；
7. 根据 A/C 与 B/C 的实际结果选择正向、接近、代理失效或明确权衡中的一种受限结论。

在这些步骤完成前，简历和面试可以说“历史预实验观察到捕获开销下降信号，随后发现算法契约、对照与正确性验证不足并完成协议加固”，不能说“PG-CG Lite 已证明性能提升”。
