## 1. 最终目标

本计划要把当前“已经有最小实现、尚无最新 GPU 结果”的分支，整理成一个可复现、可证伪、可在面试中独立讲清楚的小型推理部署优化项目。

项目最终只主张一件事：

> 从 vLLM 已解析出的默认 CUDA Graph capture-size 集合中，根据固定工作负载的真实 token 数量分布，选择不超过预算的一个子集；比较它与默认全集、同尺寸预算的非画像基线在初始化开销、padding 代理指标和服务性能上的差异。

完成项目不以“吞吐一定提高”为条件。只要实验链路正确、对照公平、原始证据完整，负结果或存在权衡的结果同样有效。

## 2. 执行原则与范围边界

### 2.1 执行原则

1. 先修可复现性阻塞项，再改算法，再补对照实验，最后整理仓库展示。
2. 每个阶段只解决一个逻辑问题；算法、实验结果和宣传材料不得混在同一提交中。
3. 每次修改前记录当前 commit 和工作区状态；每次修改后运行与风险相称的测试。
4. 没有 A6000 原始日志时，不填写、估算或润色任何 GPU 性能数字。
5. 文档、命令、代码和结果中的术语必须一致；不再把 capture-size 数量称为“graph 数量”。
6. 上游 PR #52750 只作为未合并的依赖回移，不表述为本项目创新或已被上游接受的修复。
7. 不重写公开 Git 历史，不使用强制推送；在新修复分支验证后再合并。

### 2.2 本轮路线不做的事情

- 不修改 scheduler、CUDA kernel、CUDA Graph dispatcher 或请求热路径。
- 不做在线学习、流量漂移自动检测、动态重捕获或服务自动重启。
- 不扩展到 LoRA、speculative decoding、多模态或多卡并行结论。
- 不搭建大型实验平台，不为了图表引入新的运行时依赖。
- 不声称 padding 代理指标等价于真实 GPU 延迟。
- 不把单模型、单卡、有限工作负载的结论外推为通用生产结论。

## 3. 已冻结的算法契约

这一节是后续实现、测试和文档的共同标准。若要改变其中任一条，必须先修改本计划并说明原因。

### 3.1 输入与候选集合

画像日志给出：

- 默认 capture-size 集合 `C = (c1 < c2 < ... < cm)`；
- `FULL` 和 `PIECEWISE` 事件的直方图 `H = {(x_i, w_i)}`；
- `NONE` 事件数量，仅用于报告，不参与选择。

必须满足：

- `C` 为升序、去重、正整数集合；
- 同一次聚合中的每条画像记录必须具有完全相同的 `C`；
- 每个参与选择的 `x_i` 都不大于 `M = max(C)`；
- 日志中没有有效 `FULL` 或 `PIECEWISE` 事件时直接失败，不构造虚假计划。

### 3.2 输出约束

选择结果 `S` 必须满足：

\[
S \subseteq C,\qquad M \in S,\qquad 1 \le |S| \le K
\]

其中 `K` 是 capture-size 数量预算，默认值仍为 8。保留 `M` 是为了不主动缩小默认配置已经覆盖的最大 token 上界。

这意味着：默认集合为 `[1, 2, 4, 8]` 时，即使画像中频繁出现 `3`，结果也不能包含 `3`。当前实现会得到 `(3, 8)`，这是本次必须修复的核心语义错误。

### 3.3 目标函数

对任意事件 `x`，使用结果集合中不小于它的最小尺寸：

\[
g_S(x)=\min\{s\in S\mid s\ge x\}
\]

最小化画像上的预测 padding：

\[
L(S)=\sum_i w_i\bigl(g_S(x_i)-x_i\bigr)
\]

最终排序规则固定为：

1. 预测 padding 更小；
2. padding 相同时，capture size 更少；
3. 前两项相同时，选择字典序更小的尺寸元组。

第二条允许结果真正满足“最多 `K` 个”，避免为了凑满预算捕获对画像完全没有收益的尺寸。

### 3.4 动态规划定义

候选端点只来自 `C`。若前一个已选端点是 `c_p`，当前端点是 `c_j`，则本次新增覆盖的需求为：

\[
c_p < x_i \le c_j
\]

对应区间代价为：

\[
cost(p,j)=\sum_{c_p < x_i \le c_j}w_i(c_j-x_i)
\]

首个端点使用一个负无穷哨兵，覆盖所有 `x_i <= c_j`。动态规划状态表示“使用若干个默认候选、最后停在 `c_j` 的最小代价及端点元组”。最终只比较以 `M` 结尾、尺寸数量为 `1..min(K, m)` 的状态，并按上一节的三层规则取最优。

该算法求解的是离散默认集合上的精确最优子集，不再是对观测 token 数量重新量化。

### 3.5 名称与输出契约

- Python 参数、CLI 参数和 JSON 字段统一使用 `max_sizes` 或 `max_capture_sizes`。
- CLI 将 `--max-graphs` 改为 `--max-sizes`。
- 当前功能尚未形成稳定外部 API，完成运行手册同步后不保留容易误导的旧别名。
- 计划输出应显式包含默认尺寸列表、选中尺寸列表、选择策略名称、两者的预测 padding、有效事件数和 `NONE` 事件数。
- “capture-size 数量”与“实际捕获 graph 数量”分开报告；未实际观测 graph 数量时不得用前者代替后者。

### 阶段 4：增加同预算基线并冻结实验协议

目标：区分“尺寸变少带来的收益”和“画像指导选择带来的收益”。

正式比较固定为三组：

| 组别 | 配置 | 回答的问题 |
|---|---|---|
| A：默认全集 | vLLM 默认 `C` | 原始初始化开销与稳态性能是多少 |
| B：同预算规则子集 | 不读取画像、从 `C` 选择与 PG 组相同数量的尺寸 | 仅减少 size 数能取得什么结果 |
| C：PG 子集 | 本项目从画像得到的 `S` | workload 信息是否带来额外价值 |

B 组在看结果前冻结为“默认集合的等秩子集”：按默认列表索引近似等间隔取点并强制包含最大尺寸。实现应保持确定性、无画像输入，并使用与 C 组相同的实际尺寸数量。不要在看到性能后换一个更弱的基线。

任务：

- [ ] 在现有 planner 文件和测试文件内增加小型、确定性的等秩基线函数，避免新增实验框架。
- [ ] 输出 B、C 两组可复制的 `compilation_config`，名称清楚且不会混用。
- [ ] 离线报告 `K ∈ {4, 8, 16}` 的预测 padding 敏感性；正式 GPU 主实验仍预注册 `K=8`。
- [ ] 若 C 组因等代价实际少于 8 个尺寸，B 组必须使用相同数量，而不是仍使用 8 个。
- [ ] 冻结模型 revision、输入数据生成方式、请求数、并发、输入/输出长度、随机种子和服务参数。

正式指标至少包括：

- 配置中的默认 size 数与选中 size 数；
- 画像上的默认、B 组和 C 组预测 padding；
- CUDA Graph 捕获时间与捕获显存；
- 服务从启动到 ready 的时间；
- request throughput；
- median/p95 TTFT；
- median/p95 TPOT；
- 请求错误数和 20 条固定请求的输出一致性；
- 若能从稳定现有指标直接获得，则记录实际捕获 graph 数；否则明确记为“未观测”。

运行顺序采用三轮交叉顺序，避免总让默认组先跑：

1. `A → B → C`
2. `C → A → B`
3. `B → C → A`

主实验使用同分布评测；另增加一个轻量 workload-shift 检查，例如改变并发或输入长度分布。shift 结果只用于暴露泛化边界，不扩大为第二套完整主实验。

退出条件：在任何正式 GPU 数字产生前，三组配置、顺序、指标、阈值和停止条件已写入运行手册并提交。

### 阶段 6：分析结果并给出受限结论

目标：让结论由预先冻结的指标推出，而不是由期望反向挑选数字。

分析顺序：

1. 正确性和错误数；
2. 配置 size 数、实际 graph 数（若可得）和预测 padding；
3. capture 时间、capture 显存和 time-to-ready；
4. throughput、TTFT、TPOT；
5. 同预算 B 与 PG 组 C 的差异；
6. workload shift 下方向是否保持。

主张边界：

- A 对 C 只能证明“整体方案”相对默认全集的权衡。
- B 对 C 才能支持“画像指导的选择优于任意同预算剪枝”。
- 三次重复只报告逐次值、中位数和波动范围，不做统计显著性声称。
- 若 C 不优于 B，应如实结论为“减少集合有效，但当前画像目标没有显示额外收益”。
- 若稳态性能退化超过预注册阈值，应展示启动成本与 padding 的权衡，不改阈值。

退出条件：每个结果表单元都能追溯到原始文件；没有超出单卡、单模型和已测 workload 的泛化表述。

## 6. 各阶段统一质量门禁


算法阶段还必须执行小规模暴力枚举对拍；GPU 阶段必须保留命令、环境、退出码和原始日志。只有“命令退出成功”不等于算法正确，只有“指标变好”也不等于实验公平。

每个阶段的提交说明使用中文正文或清楚的英文 Conventional Commit 标题，并在正文回答：

- 改了什么；

## 8. 项目完成定义

## 9. 完成核心路线后才考虑的扩展

下列内容仅在第 8 节全部完成后评估，不得挤占核心修复和正式实验：

- 多种真实请求长度分布与更严格的留出评测；
- 为 capture 时间或 graph memory 建立显式成本项，而不只限制 size 数量；
- 画像漂移检测与重新生成静态配置的运维流程；
- 多模型、多 GPU 架构或不同 CUDA Graph mode 的泛化验证；
- 将工具整理为可独立安装的命令行包或向上游投稿。

这些扩展是否值得做，应由核心实验暴露的问题决定，而不是为了增加项目体量。
